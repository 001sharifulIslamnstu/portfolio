ROS 2 Experiments That You Can Actually Reproduce Six Months Later

A robotics experiment is not reproducible because the code is on GitHub. Timing, parameters, bags, environment, and analysis provenance must travel together.

September 6, 2026•9 min read•Md Shariful Islam

Robotics experiments often fail to reproduce for mundane reasons: a parameter was changed manually, a topic had a different rate, a transform tree differed, a bag was recorded with missing topics, or the analysis notebook used a quietly modified CSV.

Start with an experiment manifest

Every run should have a machine-readable manifest containing the git commit, launch configuration, parameter files, robot or sensor identifiers, dataset/run ID, start time, environment notes, and software versions that matter. The manifest should be saved next to the recorded data.

Make launch files boring

Interactive setup is the enemy of repeatability. Prefer explicit launch arguments and version-controlled parameter YAML files. If an operator must click a GUI control before every run, document that step or replace it with a scripted service/action call.

Record more than you think you need

For a typical perception-to-action experiment, I would record raw or minimally processed sensor topics where practical, transforms, command topics, state feedback, decision outputs, diagnostics, and clock information. The exact list depends on bandwidth and privacy constraints, but the principle is simple: preserve enough evidence to reconstruct what the system believed and did.

Rule of thumb: if a result cannot be traced back from a plot to an immutable run ID and raw evidence, the pipeline is too fragile.

Synchronize in analysis, not by assumption

Different ROS 2 nodes can publish at different rates and with different latency. Never assume that row number 100 in two CSV files refers to the same instant. Use timestamps, define the synchronization rule, report the tolerance, and test edge cases around missing or delayed messages.

Separate raw, derived, and reported data

  • Raw: rosbag and immutable run metadata.
  • Derived: synchronized tables, features, predictions, and intermediate artifacts generated by scripts.
  • Reported: metrics, plots, and tables that appear in a paper.

Each layer should be regenerable from the previous one. This structure reduces accidental leakage, manual edits, and manuscript/code mismatches.

A practical folder pattern

I like a run-centric layout: one folder per run, containing the manifest and raw data; a separate versioned analysis package; and a generated results directory that can be deleted and recreated. Add a small verification script that checks topic presence, message counts, timestamp monotonicity, and expected duration before a run is accepted.

Reproducibility is not extra documentation after the experiment. It is part of the experimental system.

Note: This is a research note, not a peer-reviewed claim. It is meant to make a technical question precise enough to test.
